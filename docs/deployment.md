# Deployment

The deployment workflow installs one standalone relay on an AWS Lightsail instance in Stockholm (`eu-north-1`), behind Cloudflare's proxy. It serves Supaterm at `wss://relay.supaterm.com` and Supacode builds at `wss://relay.supacode.sh`, so hosts and clients on either hostname share one set of registrations. `wss://relay2.supaterm.com` reaches the same relay and names the machine.

All three hostnames are proxied Cloudflare A records for the instance's static IP, `13.63.231.197`. Cloudflare terminates public TLS and connects to [Caddy](../deploy/relay2/Caddyfile) on port 443, which presents one Cloudflare Origin CA certificate for all three. A configuration rule in each zone sets SSL to Full (strict) for these hostnames, and turns off Browser Integrity Check and the security level challenge, because native clients cannot answer a challenge. Caddy accepts only connections that present an authenticated origin pull certificate signed by a CA in `/etc/caddy/origin-pull-ca.pem`; each zone uploads its own per-hostname certificate, so requests through other Cloudflare accounts cannot reach the relay. The [firewall](../deploy/relay2/nftables.conf) accepts port 443 only from Cloudflare's published IP ranges, and SSH from anywhere; update it when Cloudflare changes those ranges.

Caddy replaces `X-Forwarded-For` with `CF-Connecting-IP` before proxying to `127.0.0.1:8080`, so the relay's per-network quotas count the visitor's address. A [drop-in](../deploy/relay2/memory.conf) at `/etc/systemd/system/supaterm-relay.service.d/memory.conf` lowers the Go memory target to 1 GiB and the service cap to 1.5 GiB for the 2 GiB machine. Caddy's file lives at `/etc/caddy/Caddyfile` and the firewall's at `/etc/nftables.conf`. These files are installed by hand; the workflow installs only the binary and service unit, and fails before installing when any live copy differs from the repository.

The [service unit](../deploy/supaterm-relay.service) binds protocol traffic to `127.0.0.1:8080` and private health and detailed metrics to `127.0.0.1:9090`. Only the local proxy may supply the client IP, and the private listener accepts loopback peers only. Public `/metrics` contains aggregate counters. The public [`/dashboard/`](https://relay.supaterm.com/dashboard/) refreshes those counters every two seconds and adds throughput, process CPU, the machine's load average and memory, and the process start time. Host traffic details stay on the private listener.

Code changes pushed to `main` run [the deployment workflow](../.github/workflows/deploy.yml): the race test suite, a Linux build, the hand-installed file check, service installation, and verified smoke exchanges between hosts registered through `relay.supaterm.com` and clients connecting through each of the three hostnames, which fail unless all three reach the same relay. Restarting the relay closes its sockets, so hosts and clients must reconnect. Each relay instance owns its authenticated registrations and pairs in memory; distributing an endpoint's sockets across independent instances is unsupported.

The [installer](../deploy/install-relay.sh) installs the binary and unit, restarts the service, and enables it once the private health check passes.

A single relay has one failure domain; this deployment does not implement automatic failover.
